The cluster constructs the optical projection frustum (the throw pyramid) of a projector from optical specification parameters.
Geometric Logic and Workflow
Target Plane Placement
Vector Translation: The cluster takes the lens origin point (Pt) and moves it along the projection axis by the throw distance (Distance D) and vertically by the lens shift offset (Offset Hd) using a Construct Vector and Move component.
Plane Construction: An XZ Plane is placed at this translated point, establishing the coordinate system of the projection screen perpendicular to the optical throw axis.
Screen Boundary Generation
Domain Calculation: The specified image width and height are divided and mapped into negative and positive bounds using division (/) and negation (-x) components to generate a centered horizontal domain.
Rectangle Construction: The Rectangle component builds the planar projection boundary on the target XZ Plane.
Frustum Geometry Assembly
Vertex Extraction: The rectangle is decomposed using Discontinuity to extract its four corner points. A List Item component isolates vertices i, i+1, i+2, and i+3.
Pyramid Faces: Four 4Pt Surface components construct triangular/quad faces connecting the original lens center point (Pt) to each consecutive pair of screen corner vertices.
Brep Join: The side faces are joined (Brep Join) into an open or capped polysurface representing the projection cone volume (Output B).
Secondary Range / Verification Branch (Lower Section)
A secondary parallel branch evaluates a secondary throw boundary (using the 5000 reference slider and checking inputs).
It constructs an extended or maximum boundary rectangle and outputs clearance or centerline vectors (L) and status indicators (I) to verify distance constraints against the room envelope.

Step-by-Step Execution Flow
Input Resolution & Type Coercion The script inspects the Grasshopper execution scope for predefined input variable names. It resolves geometric references, Rhino document GUIDs, and untyped Grasshopper data types into explicit Rhino.Geometry types (Point3d, Brep, Plane, float) via utility resolvers (resolve_geo, resolve_brep, resolve_point).
Parametric Frustum Generation If an external cone is not supplied, the script synthesizes the projector frustum internally using the Optoma optical specifications: PNG+ 1
Constructs the screen center point by translating ProjectorPt along the optical axis by throw distance Distance_D and vertically by lens shift Offset_Hd. PNG+ 1
Generates a planar projection screen rectangle centered at this point with dimensions Width × Height on an XZ plane (or an oriented plane if ProjectorPlane is provided). PNG+ 1
Generates five boundary surfaces connecting ProjectorPt to the four corners of the rectangle and caps the base. PNG
Joins the surfaces into a closed polysurface (cone_brep) using document absolute tolerance. PNG
Lens Front-Face Identification The script iterates over all sub-surfaces (Faces) of LensBrep. It computes the UV midpoint of each face domain:
um=2umin+umax,vm=2vmin+vmax
It identifies the front optical face by finding the face whose midpoint has the minimum Euclidean distance to ProjectorPt. It extracts the face normal n^ and centroid, orienting n^ towards the optical path direction.
Footprint Extraction via Surface Intersection The script computes the geometric intersection between cone_brep and the isolated lens front face via Rhino.Geometry.Intersect.Intersection.BrepBrep.
If the surface-surface intersection succeeds, the resulting curve segments are joined into a closed boundary curve (LensFootprint).
If surface intersection returns null, it triggers a fallback Boolean intersection (Brep.CreateBooleanIntersection) between the full frustum and the lens solid to extract the perimeter edge curves.
Truncated Incident Cone Construction Instead of keeping an unbounded or full throw-length cone, the script creates a ruled loft (Brep.CreateFromLoft) between the single vertex ProjectorPt and the closed boundary LensFootprint. The planar base at the lens interface is capped using CapPlanarHoles. The resulting solid represents the beam volume strictly from the projector emission pupil to the lens surface.
Thin-Lens Ray Deflection and Refraction The LensFootprint curve is divided into N equidistant parameters based on NumSampleRays. For each perimeter point Plens:
The incoming ray vector vin=Plens−Pprojector is decomposed into an axial component daxis=vin⋅n^ and a transverse component vin,⊥=vin−daxisn^.
The transverse position relative to the lens optical center is Δr⊥=(Plens−Pcenter)−((Plens−Pcenter)⋅n^)n^.
Thin-lens refraction calculates the deflected transverse direction:
vout,⊥=daxisvin,⊥−fΔr⊥
The resulting vector vout=n^+vout,⊥ is unitized.
Collimated Beam Solid Construction Each refracted ray is projected forward by VialDistance:
Pvial=Plens+vout⋅dvial
An interpolated curve is fitted through the resulting points {Pvial}. The script lofts a solid polysurface between LensFootprint and the projected vial boundary curve, capping both planar ends to generate CollimatedBeam.

Detailed Mechanics
1. C# (Native Script Component)
Execution Model: Code is compiled directly into Common Intermediate Language (CIL) at runtime and executed by the .NET JIT compiler.
RhinoCommon Binding: Zero marshaling overhead. RhinoCommon is a managed .NET wrapper around native C++ OpenNURBS; C# accesses these pointers directly.
Loop Efficiency: Tight loops performing point math, array transformations, or vector projections run at near-native C++ performance.
Parallel Processing: Direct support for System.Threading.Tasks.Parallel.For and PLINQ allows linear scaling across CPU cores for geometric intersections and ray tracing.
2. VB.NET (Legacy Script Component)
Execution Model: Compiles down to the exact same CIL instructions as C#.
Performance: Execution profile matches C# within margin of error for numeric calculations and geometric modeling.
Drawback: Deprecated in active Grasshopper development; no performance benefit over C#.
3. IronPython 2.7 (Default in Rhino 6/7, Legacy in Rhino 8)
Execution Model: Interpreted through the Dynamic Language Runtime (DLR) on top of the .NET CLR.
Bottleneck: Every object lookup, method call, and numeric operation performs runtime type checks and dynamic dispatch.
RhinoCommon Interop: Passing primitive types or arrays (such as lists of Point3d) creates overhead converting between Python dynamic types and .NET types.
Use Profile: Suitable for pipeline orchestration; unsuitable for iterative ray-bounce loops, voxelization, or thousands of Brep face evaluations.
4. CPython 3.x (Rhino 8 Script Component / Rhino.Code)
Execution Model: Standard native CPython runtime connected to the Rhino process via Python.NET (pythonnet).
Interoperability Cost: Each call to a Rhino.Geometry method crosses the C-extension boundary into the .NET CLR. For fine-grained per-vertex or per-ray loops, this interop overhead makes CPython significantly slower than pure C# and occasionally slower than IronPython.
Vectorization Advantage: When geometric operations can be cast into NumPy arrays, SciPy spatial trees (KDTree), or PyTorch tensors, computation executes in compiled native C/Fortran libraries, bypassing both the Python interpreter and the .NET runtime.

1. Why ConeBrep is Redundant
ConeBrep is no longer needed. It was retained solely as an optional override for backwards compatibility with your original Grasshopper cluster.
Since the C# script now generates the projection pyramid directly from Distance_D, Offset_Hd, Width, and Height, delete the ConeBrep input parameter entirely.
2. What FocalLength Is and Why It Cannot Be Calculated from Distance
FocalLength (f) is the intrinsic optical focal length from the lens datasheet (e.g., of the Fresnel or plano-convex collimating lens), not the physical distance between the projector and the lens.
The script already computes the physical distance automatically from geometry:
daxis=vin⋅n^
The script requires both parameters independently to model refraction via the paraxial thin-lens formula:
vout,⊥=daxisvin,⊥−fΔr⊥
daxisvin,⊥: Represents the geometric divergence of the ray exiting the projector pupil at the measured physical distance daxis.
−fΔr⊥: Represents the optical bending power (P=f1) applied by the glass/plastic at distance Δr⊥ from the lens optical axis.
If the lens focal length f were replaced with the measured distance daxis, the term daxis1−daxis1 would always equal zero, forcing the output to falsely report perfect collimation (vout,⊥=0) regardless of where the projector is physically placed. To verify whether your physical setup achieves telecentricity, the script must compare the measured distance against the fixed datasheet focal length f. Collimation only occurs when the physical distance matches f.

The best solution is to define a Local Reference Plane (Coordinate Frame) rigidly attached to the projector in its rest position, and pass that plane through the exact same transformation pipeline as the projector CAD geometry.
Why a Reference Plane is Superior
Fully Constrains all 6 Degrees of Freedom (6 DOF)
A Point only provides 3 translations (X,Y,Z); it carries zero rotational data.
A Vector only provides 2 rotations (pitch and yaw); it has no origin point and loses roll (chassis tilt).
A Plane encapsulates origin (X,Y,Z) and three orthonormal axes (X,Y,Z), defining position, throw axis, vertical offset direction, and horizontal screen alignment simultaneously.
Transforms Natively in Grasshopper
Grasshopper transformation components (Move, Rotate, Rotate Axis, Orient) accept Plane directly into their geometry (G) input.
Unlike vectors (which corrupt when passed into position-based components like Orient), a Plane transforms rigidly alongside the projector Brep without mathematical distortion.
Decouples Hardware Dimensions from Scene Placement
Optical offsets (Offset_Hd, lens center position relative to chassis mounting holes) are defined once in the projector's local rest coordinates.
Moving or tilting the projector in the scene automatically moves the optical emission vector and screen rectangle with zero manual recalculations.

A plane constructed strictly from a point and a normal vector (Plane Normal) mathematically cannot determine the roll angle. A normal vector defines only 2 rotational degrees of freedom (pitch and yaw). Rhino computes the remaining two orthogonal axes (X and Y) by crossing the normal with an arbitrary world axis (typically World Z). If the physical projector rolls 90° around its optical axis, the normal vector does not change, causing the roll information to be erased.
The Fully Automatic Solution: Extract the Plane from ProjectorBrep
To determine the exact orientation (pitch, yaw, and 90° roll) without manual transforms or rest points, pass the Projector CAD Brep directly into the script.
The projector geometry physically contains its own coordinate system:
Optical Axis (Z): The surface normal of the front lens face (or the face closest to the lens apex).
Chassis Up-Vector (Y): The direction along the short dimension of the front face (or the local vertical edge of the projector chassis).
Chassis Right-Vector (X): The cross product of the Optical Axis and the Chassis Up-Vector.
Grasshopper Method: Extract Plane Directly from the CAD Face
Before using C#, this can be resolved natively on the canvas:
Connect the transformed projector CAD body to a Deconstruct Brep component.
Filter the faces using List Item to pick the front flat face surrounding the lens.
Connect that face to an Evaluate Surface component evaluated at {0.5,0.5} (with surface reparameterized).
The output Frame of Evaluate Surface is the true local plane:
The frame normal points along the optical throw.
The frame U and V tangent vectors point along the chassis width and height, preserving the 90° roll.
Wire that frame directly into ProjectorPlane.
